# Fotos no Amazon S3

Bucket configurado na aplicação: **alugueis-pelada**, região **sa-east-1**. Os objetos ficam em `alugueis/<id-da-pelada>/<id-aleatorio>.<extensao>`. Mantenha o bucket privado, com bloqueio de acesso público e ACLs desabilitadas. O Angular envia e lê as fotos pela API. A consulta das fotos de aluguéis concluídos é pública; uploads e demais alterações exigem autenticação. Fotos de peladas em andamento e canceladas não são expostas anonimamente. Não é necessário CORS no bucket nem tornar os objetos públicos.

## Segredos locais do .NET

No projeto `backend/Pelada.Api`, abra **Gerenciar Segredos do Usuário** e preencha o `secrets.json`:

```json
{
  "AWS:AccessKey": "SUA_ACCESS_KEY",
  "AWS:SecretKey": "SUA_SECRET_KEY",
  "PhotoStorage:Provider": "S3"
}
```

Se as credenciais forem temporárias, adicione `AWS:SessionToken`. Não envie as chaves pelo chat nem salve esse arquivo dentro do repositório. O SDK Web carrega os User Secrets em `Development`.

O `UserSecretsId` do projeto é `pelada-manager-api`. No Windows, o arquivo correto fica em:

```text
%APPDATA%\Microsoft\UserSecrets\pelada-manager-api\secrets.json
```

Bucket e região são configurações públicas em `appsettings.json`; não é preciso colocá-los nos segredos. A identidade IAM dessas chaves precisa da política de [acesso às fotos](../infra/aws/s3-photos-policy.json), limitada ao prefixo `alugueis/*`.

## Docker Compose no Windows

Depois de preencher o arquivo, execute na raiz do projeto:

```powershell
docker compose -f compose.yaml -f compose.secrets.yaml up --build -d --wait
```

O segundo arquivo seleciona S3 e monta somente `secrets.json` como arquivo de leitura no container da API. O Docker não copia as credenciais para a imagem. Se o arquivo não existir, o Compose recusa o bind em vez de criar uma pasta vazia.

Para testar as credenciais e permissões com um arquivo temporário:

```powershell
docker compose -f compose.yaml -f compose.secrets.yaml exec -T api dotnet Pelada.Api.dll --check-s3
```

O comando envia uma pequena imagem de teste ao prefixo `alugueis/_verificacao/`, lê e compara os bytes e remove somente o objeto que acabou de criar. Só retorna sucesso quando as três operações funcionam. Nenhuma credencial é exibida. Com versionamento habilitado, a exclusão normal preserva versões anteriores conforme a configuração do bucket.

Após trocar as chaves, recrie a API com o mesmo comando de `up`. Use sempre os dois arquivos Compose neste modo; o Compose base sozinho seleciona `Database` por padrão. O modo sem credenciais continua disponível para desenvolvimento local e testes.

## Hospedagem

`compose.secrets.yaml` é apenas para desenvolvimento local no Windows. Em produção, utilize uma IAM role ou outro mecanismo de credenciais do ambiente AWS, selecione `PHOTO_STORAGE_PROVIDER=S3`, mantenha `S3_BUCKET=alugueis-pelada` e `S3_REGION=sa-east-1`, e configure a origem HTTPS normalmente. Sem `AWS:AccessKey` e `AWS:SecretKey`, o SDK utiliza sua cadeia padrão de credenciais, incluindo IAM roles.

## Persistência e compatibilidade

- Novos uploads em modo S3 guardam somente bucket, região, chave e metadados no PostgreSQL; os bytes vão para o S3.
- Fotos antigas no PostgreSQL continuam legíveis. Elas não são transferidas ou apagadas automaticamente. Ao substituir uma foto, o novo upload utiliza o provedor selecionado.
- Um erro no S3 não causa uma troca silenciosa para o banco nem confirma um resultado sem foto.
- Cada upload usa uma chave nova. A referência no banco só muda após o envio; a foto anterior é removida do S3 depois da gravação. Se a limpeza falhar, o objeto é mantido e o servidor registra uma mensagem sem credenciais.
- Se houver falha no banco, um objeto novo só é removido se o banco confirmar que ele não está referenciado. Se o resultado da transação for incerto, o objeto é preservado para evitar apagar uma foto válida.
- O dump do PostgreSQL preserva fotos antigas e referências às novas fotos; os objetos S3 precisam de sua própria política de proteção/backup. A exportação JSON continua sem os arquivos das imagens.

## Verificação automatizada

Os testes usam PostgreSQL real e S3 simulado. Verificam metadados, substituição, falhas, concorrência, limpeza e leitura de fotos antigas, sem acessar a AWS. O SDK oficial também tem testes com cliente de teste. O acesso ao bucket real só é comprovado por `--check-s3` com credenciais válidas.

Referências: [credenciais do SDK .NET](https://docs.aws.amazon.com/sdk-for-net/v4/developer-guide/creds-assign.html) e [configuração do SDK](https://docs.aws.amazon.com/sdk-for-net/v4/developer-guide/net-dg-config-netcore.html).
